# Stripe registration deployment

Registration uses Stripe Payment Elements and card PaymentIntents with manual capture. The server captures an authorization only while the reservation is pending and its 15-minute deadline has not passed. A browser success callback alone never confirms registration.

## Configuration

Set `PAYMENT_PROVIDER=stripe`, `STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY`, `STRIPE_WEBHOOK_SECRET`, `MONGODB_URI`, and `CRON_SECRET` on the API deployment. Use matching Stripe test keys for staging and matching live keys only for an approved live rollout. No secret key belongs in a VITE variable. MongoDB must support transactions (Atlas or a replica set).

Configure a signed Stripe endpoint at `/api/payments/webhook` for:
- `payment_intent.amount_capturable_updated`
- `payment_intent.succeeded`
- `payment_intent.payment_failed`
- `payment_intent.canceled`
- `charge.refunded`
- `charge.dispute.created`

Invalid signatures return 400. Processing failures return 500 so Stripe retries. Declined attempts remain retryable until expiry. Capacity creation/release and reservation transitions commit together. Repeated cancellation/reconciliation cannot release capacity twice. An uncertain Stripe cancellation retains capacity until its outcome is known.

## Expiry on Vercel Hobby

Hobby supports daily cron only, so committed cron schedules provide daily recovery. The checkout timer triggers cancellation at expiry; browse/reserve requests also reclaim expired holds. Authorizations received after the deadline are cancelled without capture, independently of the cron schedule. An abandoned, unpaid intent can remain uncancelled until the next browse/reserve request or scheduled cleanup; it cannot be captured by the application after expiry. For prompt background cleanup when there is no traffic, run `/api/cron/expire` every minute and `/api/cron/reconcile` every five minutes using Vercel Pro or an external scheduler, with `Authorization: Bearer <CRON_SECRET>`.

## Verification

`npm --prefix backend test` runs reservation race and payment-state tests against an isolated local MongoDB replica set with a fake payment provider. It does not load-test Stripe or touch the application database.

Frontend: `npx tsc --noEmit` and `npm run build`. API: `npx tsc -p tsconfig.api.json --noEmit`.

Staging browser checks should cover actual Stripe form loading, successful test-card authorization/capture, declined card retry, refresh recovery, explicit cancellation, navigation cancellation, and server-confirmed success. Test cards are documented at https://docs.stripe.com/testing.

## Existing limitations before live rollout

The application's existing sign-in is demo/local-storage based, and API player identity is supplied by email. This change does not introduce production authentication or authorization. Replace that identity model before accepting real money. Reservations created using the previous mock adapter are not treated as real Stripe purchases. Review existing capacity/data before a production migration. Refunds and disputes are recorded without automatically releasing a registered league slot; organizer decisions remain separate from unpaid checkout cancellation.

## Data provenance statement

The current database counts are test data only. The player records, tournament histories, and reservations were generated by the repository's seed script and by manual application testing. They are not identified as real customers, and this evidence pack makes no claim that they have a real-user consent basis. They must be deleted or replaced with approved production data before launch. The seed script documents 500 generated players and 120 generated tournament-history records; the larger review count of 504 players and 69 reservations reflects later test activity in the shared test database.
